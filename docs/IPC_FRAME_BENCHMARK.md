# 帧面选型基准报告（#516 / ADR-0009 B2）

> 日期：2026-08-19　机器：AMD Ryzen 5 9600X / 31GB / Windows 10 专业版 build 19045
> Harness：`crates/aerodesk-ipc/examples/ipc_frame_bench.rs`（`cargo run -p aerodesk-ipc --example ipc_frame_bench --release`）
> 判定预算（ADR-0009 B2）：F1 的 p95 附加延迟（写入 → 消费侧帧完整可用）**< 5ms**。

## 1. 方法学

- **测量量**：单帧单向附加延迟——生产者在写入起始时刻打点 `t0`，消费侧在「感知到帧到达」（`wake`）与「帧完整拷入消费侧缓冲」（`total`，≈ UI 可呈现）各取一次；预热 50 帧后采样 **N=1000**，报 p50/p95/p99。
- **ping-pong 协议**：生产者须等消费侧取走上一帧再发下一帧（shm 用 ready/taken 双事件、pipe 用时间戳槽位换手、memcpy 用原子标志自旋），与 B4 部署形态「解一帧呈一帧」一致；有效带宽 = payload / p50(total)，为单帧往返口径而非流式峰值。
- **载荷**：1080p RGBA 8,294,400B、4K RGBA 33,177,600B；F2 代理载荷 256KB（高码率 P 帧量级）/ 1MB（IDR 量级）——F2 经管道转发的传输成本。
- **同进程两线程**：loopback 命名管道与共享内存的内核路径与跨进程一致（CreateFileMapping 页面文件后备、管道内核缓冲），跨进程仅多出边际上下文切换差；B4 落地时以同 harness 双进程复测确认。

## 3. 解读

1. **shm ≈ memcpy 下限**：F1 在两种分辨率下与进程内拷贝基线的差距 <0.04ms——共享内存 + 事件通知本身不引入可测开销，全部成本是两次必然存在的拷贝（host 解码写入映射、desktop 拷入 Slint 图像）。
2. **管道在 4K 越预算**：1080p（8MB）尚可追平（0.75ms），4K（33MB）p95 达 6.12ms、带宽近乎腰斩——字节流经 1MB 内核缓冲分块倒手，拷贝次数与 syscall 次数随尺寸线性放大。故帧面不选管道；管道保留为控制面载体（消息 <64KB 时延迟 ~0.02ms 量级，见 256KB/1MB 行外推）。
3. **F2 的传输成本可忽略**（1MB 编码帧 p95 0.17ms），但 F2 的真实代价不在传输：desktop 需保留解码栈（FFmpeg/VideoToolbox 分发、硬解兼容矩阵），ADR-0009 的「UI 壳瘦身」目标缩水为「引擎出、codec 留」，且每帧多一次完整解码的确定性延迟。仅作 F1 受阻时的回落项。

## 4. 结论

**选 F1（共享内存环形帧面 + 事件通知）**：p95 附加延迟 1080p 0.75ms / 4K 3.09ms，均满足 <5ms 预算（4K 余量 38%），desktop 完全不链接解码栈。无需启用方案 B（主控留 UI 进程）回落。

B3/B4 落地约束（随本结论进入协议 §4）：

- 共享内存按 `Local\aerodesk-frame-<session>` 命名，双槽环形（4K×2 = 64MB 上限）+ ready/taken 双事件换手，即本基准的同构协议；
- 桌面 UI 崩溃/挂起时 host 侧写超时（taken 事件等待上限）即回收该会话帧面，不阻塞引擎；
- macOS/Linux 帧面载体（`shm_open`+`mmap` / mach_vm 或 XPC）在对应平台批次另测，本报告口径仅覆盖 Windows 先行范围。
