# ADR-0009：进程模型——host 统管会话引擎（主控+被控），desktop 退为纯 UI/UX（#508）

- 状态：已采纳（2026-08-18 提议；2026-08-19 B1 完成落地，转入实施）
- 关联 Issue：#508（母单，含 B1–B4 批次拆分）、#470（服务 presence/仲裁）、#471（登录界面 helper）、#472（UAC 穿透）、#473（安装器/服务注册）、#492（host 从 cli 拆出）
- 相关 ADR：ADR-0008（线程模型——本 ADR 不改变服务/引擎内部的 std::thread 同步模型，IPC 线程治理同样遵循其原则）
- 决策：**目标进程模型为 aerodesk-host 统管全部会话/媒体引擎（主控 + 被控），aerodesk-desktop 退为纯 UI/UX 壳，两者经 loopback IPC 通信**；按 B1 引擎下沉 → B2 IPC 协议 → B3 被控迁移 → B4 主控迁移分四批落地，任一批次可独立验收、独立回退。

## 背景

当前进程模型（main，#492 之后）：

1. **aerodesk-desktop 承载 UI 与全部会话引擎**：主控 viewer（`generic_media`/`macos_media`）与被控 publisher（`generic_publisher`）都以线程跑在 UI 进程内，UI 直接持有 str0m endpoint 与媒体 socket。
2. **aerodesk-host 只有被控服务面**（#470 M2/M3）：SYSTEM 常驻 presence + WTS 会话仲裁 + 登录后拉起 desktop 让位；登录界面/安全桌面出流由 #471 在建。
3. **aerodesk-agent 独立复用 aerodesk-core 引擎**跑通全媒体链路——证明引擎层可脱离 UI 进程复用。

痛点：

- **会话生命周期绑死 UI**：UI 崩溃/被关闭即全部会话（含进行中的文件传输）死亡，无挂回能力。
- **无统一会话仲裁**：多会话、多 UI 实例、未来第二前端（web/移动/命令行）各自为战；被控侧 #470 已建立的仲裁只覆盖 presence 层。
- **被控跨权限/会话边界**（登录界面、UAC、锁屏）必须落到 SYSTEM 服务 + helper，引擎留在 UI 进程则这条线永远缺一角。
- **UI 迭代拖着媒体栈编译**（Slint + ffmpeg + 平台采集全在一个 crate），desktop 无法独立瘦身。

业界对照：ToDesk 为双进程服务化（SYSTEM 服务 + 用户态 agent，loopback IPC）；RustDesk 服务管被控、主控媒体留在 UI 进程。两者被控侧一致收进服务，分歧在主控侧归属。

## 候选方案对比

| 方案 | 优点 | 代价 | 结论 |
|---|---|---|---|
| **A. 全量服务化**：主控+被控引擎都进 host，desktop 纯 UI | 会话/UI 生命周期解耦（UI 死了会话不死、重开可挂回）；统一仲裁；多前端复用引擎；desktop 大幅瘦身；被控全状态面（登录前/后/锁屏）路径统一 | 帧通路过 IPC（共享内存/编码流），延迟与复杂度；调试需先分界 UI/服务；工程量大（四批） | **选定（目标态）** |
| B. 业界主流折中：服务只管被控，主控留 UI 进程，引擎抽共享 crate | 无帧 IPC；工作量小一档 | 主控会话仍绑 UI 生命周期；仲裁不统一；未来第二前端仍要重写主控编排 | 不选为目标态；其引擎下沉步骤与 A 的 B1 完全相同，保留为任一后续批次的回退位 |
| C. 维持现状（desktop 全承载） | 零迁移成本 | 痛点全留；#471 完成后被控仍双路径（helper 出流 vs UI 出流） | 不选 |

## 决策

1. **host 为双进程宿主**：
   - **SYSTEM 服务**（已有）：被控仲裁、安全桌面/helper（#471/#472）、机器级配置；
   - **用户态 agent**（新增）：主控 viewer 引擎、登录后被控出流。主控不跑 SYSTEM——session 0 隔离对主控只有害处（看不到用户桌面交互、徒增权限面），对标 ToDesk 双进程。
2. **desktop 退为纯 UI/UX**：不再直接持有 str0m endpoint / 媒体 socket（目标态）；经 IPC 完成会话建立、帧呈现、输入转发、授权与设置同步。
3. **IPC（B2 定义）**：命名管道 loopback；控制面 JSON（版本化），帧面在共享内存与编码流直连之间以实测数据选型（B2 验收强制附基准）。基准对比维度除带宽/延迟外必须含**「UI 进程是否仍需链接解码栈」**：编码流直连意味着 desktop 瘦身范围缩水为「引擎出、codec 留」（FFmpeg/VideoToolbox 仍随 UI 分发），与纯壳目标存在张力；共享内存（1080p RGBA 帧 ~8MB，memcpy 亚毫秒）与 <5ms p95 预算自洽且保持 desktop 不链接 codec。
4. **落地顺序**（每批独立 PR/验收）：
   - **B1 引擎下沉**：`generic_media`/`generic_publisher`/`macos_media` 会话编排层抽为 `aerodesk-session` crate，desktop/host 均链接；行为等价（现有 UI e2e + 冒烟全绿）。B1 是 A/B 两案共需，先行不锁定终局。
   - **B2 IPC 协议**：控制面消息集 + 帧面选型基准 + 版本化策略。
   - **B3 被控迁移**：用户态被控出流收进 host agent，与 #471 helper 共用采集路径；desktop 仅留授权开关/状态。
   - **B4 主控迁移**：viewer 迁 agent，UI 关闭会话不死、重开挂回、多会话仲裁收口。
5. **平台顺序**：先 Windows 跑通（与非登录态路线一致），macOS/Linux 服务化随后单独立项；macOS 侧 `macos_media` 仅在 B1 中原样搬迁，不改实现。macOS 子项的**已知风险**必须在立项时点名：TCC 的屏幕录制/辅助功能授权按**二进制签名身份**记录，重签名/换路径后授权静默失效（本仓库已踩 ad-hoc cdhash identity mismatch）——出流迁服务侧等于新增一个需授权的二进制身份，「权限身份迁移与重新授权 UX」（双进程分别授权引导，对齐 ToDesk mac 形态）是该子项的设计前置，不可落地后再补。
6. **发布节奏**：B3 完成前发布物维持 desktop+cli；host 进 MSI/服务注册随 #473 在 B3/B4 间合入。

## 后果

正向：

- 会话/UI 解耦：UI 崩溃、关窗、多开不再杀伤会话；大文件传输等长任务存活于服务。
- 被控能力面完整：登录前（#471）、登录后、锁屏走同一服务侧出流路径，无双实现。
- 引擎一处维护多处复用：desktop、cli、未来第二前端共享 `aerodesk-session`；UI 与技术栈迭代解耦（desktop 只剩 Slint 壳）。
- 仲裁收口：多会话上限、呼叫竞争、授权策略集中在 host，UI 不再各自实现。

代价：

- **帧通路延迟下界**：共享内存方案预计增加亚毫秒级拷贝，编码流方案增加一帧级；B2 必须用实测数据收口，超预算（目标：<5ms p95 附加延迟）则回落方案 B（主控留 UI）。
- 部署/排障复杂度：双 host 进程 + UI 三进程模型；需要统一的日志落点与会话 ID 贯通（沿用 #470 ProgramData 日志约定）。
- 职责边界治理成本：SYSTEM 服务与用户态 agent 的职能必须严格按"是否需提权/跨会话"划分，防止 agent 里的功能被顺手塞进服务扩大权限面。
- B1–B4 期间 desktop 与 host 存在双套出流路径并存的过渡态，每批次的验收必须把"切换开关/回退位"写明。
